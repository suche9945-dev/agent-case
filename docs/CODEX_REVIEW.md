### R2 · P2 · 合法的前导空格标题会使后续目录整体错位

- **位置**：`src/lib/headings.ts:112`；`src/components/guides/Markdown.tsx:33`、`:42`。
- **复现 Markdown**：

```markdown
## first
  ## indented
## last
## a
## a
## a-1
```

- **实际生产结果**：完整临时样本渲染出六个 h2，而正则漏掉 indented，只抽出五个。渲染器再按游标分配 ID，得到 `first→first`、`indented→last`、`last→a`，末尾 a-1 没有 ID；目录的 last 跳到 indented。见 [真实 DOM](CODEX_REVIEW_EVIDENCE-20261021/markdown-fixture.json) 和 [截图](CODEX_REVIEW_EVIDENCE-20261021/markdown-fixture.jpg)。
- **影响**：当前五篇规范写法暂未触发；后续合法 Markdown、引用或嵌套标题可能触发。仅“共用一个数组”并没有消除 Markdown 解析语法差异。
- **最小建议**：在同一 Markdown AST 处理链上提取标题、分配 ID、生成 TOC；至少补“生产渲染后目录文字等于目标标题”的集成测试。若短期只补前导空格正则，仍要覆盖嵌套标题，避免游标再次错位。

### R3 · P2 · 去重只统计原始 base，生成后缀仍会撞 ID

- **位置**：`src/lib/headings.ts:31`。

## 8. 后续提交与 PR 建议（本轮不执行）

保留现有历史，只对当前尚未提交改动拆分。建议顺序：

1. 导入工程：`scripts/import-guides.mjs`、`scripts/verify-import.mjs`。
2. 页面及标题：Markdown/目录/page/CSS、`scripts/verify-headings.mjs`、package/lock。标题测试应跟随标题生产逻辑，而非单纯因为位于 scripts 就归入导入提交。
3. Cursor 教程：只放 cursor 源文、该篇六张/补拍图、对应工具 YAML，以及**仅该篇变更的 JSON hunk**。
4. TRAE 教程：同样只含该篇源文、资产、工具 YAML、对应 JSON hunk。
5. Harness 教程：同样按篇提交。
6. 即梦教程：同样按篇提交。
7. 可灵教程：同样按篇提交。
8. 交付材料：DELIVERY、来源台账、自检与早晨清单；独立验收报告/证据可另作验收资料提交。

`data/guides.json` 当前五篇都有变更，不能在第一篇提交时把整份都暂存。可在最终导入后使用 `git add -p data/guides.json` 按篇选 hunk，并检查暂存 diff；若 hunk 跨篇应拆 hunk。更严格的逐提交可重建方案，是在隔离临时目录中使用“本次暂存源文集合”生成对应 JSON，再暂存该版本，最终工作区仍恢复为五篇最终生成物。不要为了拆提交丢弃其他四篇改动，不要用 checkout/reset --hard，不要 amend/rebase 既有历史。

若工具字段必须集中提交，可以在教程提交前单独做工具数据提交，但仍需五个独立教程提交，每篇包含自己的资产和对应生成物变化。发布前检查每个 commit 的暂存内容、每篇来源/实操状态和最终 import/build/typecheck。

早晨清单第 7 节的 PR 正文含“本轮改动未提交”“五篇未实机”等暂时状态。**真正提交并准备发布 PR 时**，应按届时真实状态重写，更新截图数量、已验证版本、未完成项与本次复核问题的修复状态，不能原样复制为最终完成声明；也不能在截图未补时删掉缺口说明。此轮仅提出建议，未创建 PR。
